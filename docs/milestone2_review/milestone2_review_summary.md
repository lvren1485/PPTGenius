## <a name='-1'></a>二、技术架构

### <a name='-1'></a>2.1 架构演进概述

M2 阶段系统架构从 M1 的单体 Workflow 重构为三层 Agent 架构：

```
浏览器 ──HTTP/SSE──  FastAPI (展示层)
                         │
        ┌────────────────┼────────────────┐
        │                │                │
   ┌─ api/ ─┐    ┌─ agent/ ─────┐  ┌─ infrastructure/ ─┐
   │ routes │    │ coordinator  │  │ config  │ rag(BM25)│
   │ deps   │    │ outline      │  │ db      │ ppt_engine│
   │ SSE    │    │ ppt          │  │workspace│ utils     │
   └────────┘    │ common       │  └────────────────────┘
                 └──────────────┘
```

三层依赖关系：api -> agent -> infrastructure。Infrastructure 层零向上引用。

### <a name='Agent'></a>2.2 Agent 协调层

Coordinator Agent 负责意图分类与任务分发：

```
用户消息 -> POST /api/chat/send -> Coordinator Agent (意图分类)
                                        |
                  ┌─────────────────────┼─────────────────────┐
                  v                                           v
         Outline Agent                              PPT Agent
         (Generator-Evaluator 循环)                 (两阶段流水线)
```

### <a name='OutlineAgentGenerator-Evaluator'></a>2.3 Outline Agent — Generator-Evaluator 循环

StateGraph 流程：`generator -> evaluator -> {continue -> generator, stop -> finalize}`

- Generator：4 个工具（search_knowledge, search_web, fetch_web, write_outline）
- Evaluator：1 个工具（submit_evaluation），0-10 分评分
- 三种评估模式：max_iteration / pass_score / mix（默认，阈值 8 分，最大迭代 3 次）

### <a name='PPTAgent'></a>2.4 PPT Agent — 两阶段流水线

Phase 1：StyleAgent 选择配色方案与布局模板
Phase 2：SuperFreedom Dispatcher 并发生成所有幻灯片（asyncio.gather + semaphore 限流，最多 3 轮重试）
Assembly：收集 Agent 输出 -> 构建 instruction JSON -> python-pptx 渲染 -> 快照存储

PPT 生成策略经历三次迭代：sub_agent（多 Agent 分工，存在元素覆盖问题）-> freedom（单 Agent 受限于固定布局）-> super_freedom（当前方案，Agent 完全创作自由）。

### <a name='-1'></a>2.5 技术栈

| 层级 | 技术选型 |
|:-----|:---------|
| 后端框架 | Python 3.12, FastAPI, Uvicorn |
| Agent 框架 | LangGraph + LangChain create_agent (ReAct tool-calling) |
| LLM 服务 | DeepSeek API (deepseek-v4-flash), OpenAI 兼容 SDK |
| RAG 检索 | BM25（rank_bm25）+ pickle 持久化 + jieba 中文分词 |
| 数据库 | MySQL + asyncmy, SQLAlchemy 2.0 async engine |
| PPT 引擎 | python-pptx（原生图表/表格/形状）, cairosvg（SVG->PNG） |
| 前端 | Vue 3 + Element Plus + TypeScript, Vite 构建 |
| 配置管理 | .env + config.yaml |

## <a name='-1'></a>三、核心功能实现详解

### <a name='RAG'></a>3.1 RAG 与知识库管理

- 多源数据解析：支持 PDF、Word、PPT、CSV、XLSX、TXT、MD 等格式解析，大表格数据提取特征值（最大/最小值）并截取前 100 行存储
- 网络工具集成：集成 DuckDuckGo 搜索引擎，LLM 获取 URL 后进行内容抓取与清洗，并将网络文本纳入知识库索引
- 知识库隔离机制：BM25 索引按用户隔离（`bm25_index_{user_id}.pkl`），支持用户对知识文件进行增删改查，可选择关闭网络工具
- 索引持久化：pickle 序列化，启动时加载，免重建（<100 文件、<10MB 文本时重建 <200ms）

### <a name='-1'></a>3.2 多轮迭代生成机制

- Generator-Evaluator 循环：生成器调用工具生成大纲，评估器基于问卷（含结构完整性、视觉元素、长度等指标）评分
- 质量阈值控制：设定 8 分阈值，若评分低于阈值，系统将评估结果反馈给生成器优化，最大迭代次数 3 次
- 人机交互闭环：用户在前端查看大纲结构，提供反馈意见并要求 Agent 修改，形成"系统生成-用户反馈-系统优化"的第三层交互循环

### <a name='PPT'></a>3.3 PPT 生成策略演进

- 多 Agent 方案（sub_agent）：Chart/Text/Shape 三个 Agent 独立并发生成，存在元素覆盖与协调问题，已废弃
- 单 Agent 受限方案（freedom）：单 Agent 被限制在固定布局容器内，背景大面积留白，已废弃
- 当前方案（super_freedom）：Agent 完全创作自由，模板仅为参考信息注入 Prompt，自由决定元素 position/size/style

### <a name='PPT-1'></a>3.4 指令系统与 PPT 引擎

- JSON Schema 指令系统：6 种元素类型（textbox/table/picture/shape/background/chart），Agent 通过 read_instruction() 读取
- 7 种内置布局：title_slide/section/content_bullet/content_two_column/content_three_column/content_grid_2x2/ending
- 182 种可用形状 + 5,800+ Tabler SVG 图标
- python-pptx 原生图表：8 种类型（column_clustered/line/pie/doughnut/bar_clustered/area/radar/scatter）

### <a name='-1'></a>3.5 并发调度与容错

- Dispatcher 为纯代码节点（无 LLM），以 asyncio.gather 并发处理所有 slides
- Semaphore 限流（`_MAX_CONCURRENT_SLIDES`），最多 3 轮重试
- 每 slide 获取独立 DB session 避免并发写入冲突
- SSE 实时进度推送（slide_start / slide_end / retry_round 事件）
- 相邻页上下文注入（前后各 2 页的标题 + layout_type）

## <a name='-1'></a>六、评审意见

以下为评审人对本阶段项目成果的详细意见与建议：

**1. 达思睿**

目前系统的 BM25 检索溯源率只有 50 分，离 80% 的目标还有不小差距。这说明单纯依靠关键词匹配有时难以准确召回真正支撑大纲内容的证据片段。接下来的改进建议有两个方向：一是在检索流程中引入重排序（Re-rank）环节，对 BM25 召回的候选片段用更精细的模型做二次打分，把真正相关的证据往前排；二是尝试换一个轻量级的 Embedding 模型（比如 bge-small），把知识库文本向量化后进行语义检索，弥补 BM25 对同义词、语义泛化能力不足的问题。通过这两条路径的尝试，争取把可追溯性提升到 70% 以上，让用户看到的内容"有据可查"，增强系统的可信度。

**2. 张启政**

目前的项目 PPT 生成效果是非常不错的，本次汇报的 PPT 即是项目生成的。目前的缺点是生成速度太慢。或许可以尝试简化在生成 PPT 过程中生成-评估的循环，可以尝试更低的评分阈值（当前 >8/10 才会发布）或者简化评分准则，测试生成 PPT 的效果是否和当前效果差距不大。总体项目完成度很高。

**3. 张亚东**

## <a name='Milestone3'></a>十一、下阶段行动计划 (Milestone 3)

基于本次会议评审意见与当前项目问题，制定 M3 行动计划如下：

**1. 可追溯性评分方法改进**

问题：当前 BM25 Top-1 Chunk 匹配评分（57.8 分）与 80% 溯源率目标存在差距，评分阈值尚未明确。
计划：引入句子级别二分类判定（BM25 score >= 阈值 -> 可追溯），以中位数或百分位数自适应设定阈值，替换当前连续平均分。目标在 M3 前将可追溯句子占比提升至 60%+。

**2. 外部评分机制引入**

问题：当前结构评分仅依赖内部 Evaluator Agent（均值 8.19/10），缺少外部验证。
计划：邀请 3-5 位外部用户进行独立评分，收集结构完整性、内容准确性、视觉美观度三维度数据，与内部评分进行对比分析。

**3. 多领域测试覆盖**

问题：当前 14 次测试对话集中于科技/教育领域，商业、医疗等场景覆盖不足。
计划：新增至少 3 个领域（商业汇报、医疗科普、学术论文）各 2 次端到端测试，评估跨领域生成质量差异。

**4. 性能优化**

问题：大纲生成耗时 6-7 分钟，PPT 生成耗时 7-8 分钟，约 10% 概率触发指令重试。
计划：分析 LLM Thinking 阶段耗时分布；探索 Prompt 精简与缓存命中率提升方案，目标将端到端耗时降低 20%。

**5. 代码质量整改**

问题：代码规范评审发现 P0-P3 共 5 项改进项。
计划：M3 前完成 P0（消除 _rationale_store 模块级可变状态）与 P1（补充 3 处缺失文档字符串），P2/P3 根据排期酌情推进。

**6. 文档与交付物完善**

问题：技术报告、使用说明书等文档尚待编写。
计划：完成最终技术报告撰写、代码整理与注释补全、开源准备（LICENSE、README 完善）。
